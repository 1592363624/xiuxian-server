# L3（玩家自建内容）可行性研究

> 对应 `docs/HANDOFF.md` §4.3。§4 是"还没做的设计决策（等产品判断）"，本文只做
> 可行性分析与方案对比，不改任何业务代码。

## 0. 结论摘要

1. **L3 在本项目的可行定义**：玩家用**白名单词汇表**拼装一个游戏对象，服务端
   重新校验/换算/预算裁决后落库为 `player_made` 对象，运行时走**既有解析器**生效。
   不做"玩家写代码"，也不开放任意数值。
2. **项目里已经有一个完整样板**：自创功法（L1 数值分配 + L2 词条）——
   词汇表、预算、spec 解析、归属落库、战斗侧聚合 resolver、上限、测试全都有。
   L3 不需要发明模式，需要的是**把样板通用化**并补**治理**。
3. **但样板只有服务端闭环**：`TechniqueCreationService` 全仓只被自己的测试引用，
   没有指令 / REST / WebSocket 入口。"L1/L2 已实现"指的是
   "创造 → 落库 → 战斗生效"这条链，玩家目前还摸不到。
4. **真正要建的是共享基座**（玩家内容表 + 校验器 + 动态注册表 + 举报/下架 +
   配额/经济），单个对象类型反而是增量的。建议顺序：
   **Phase 0 补 L2 入口 → Phase 1 基座 + 自建传送阵 → Phase 2 自创秘境 → 其后视数据**。
5. **最大的产品决策不是技术**：玩家自建内容是**私有**（只有自己能用）还是
   **公开**（别人能用、可收费/可举报）。私有制可以把治理成本压到接近零，
   公开制必须先有举报 + 人工下架，否则会变成脏话墙。

## 1. 背景与现状核实

### 1.1 文档原文

> L1（数值分配）、L2（效果组合）已实现。L3（玩家自建内容）、L4（脚本）没动。
> **结论是：永远不要在执行进程里跑玩家代码**，走声明式 DSL。

§4.2（传送阵）还点名了"复用**玩家自建对象**那套 L3 基础设施（和自建秘境同源）"，
说明设计意图是：**一个基座 + 多种对象类型**，不是每做一个玩法造一套。

### 1.2 L1/L2 到底实现到什么程度（逐个文件核实）

| 环节 | 实现 | 位置 |
|---|---|---|
| 数值预算（总量 / 软上限翻倍 / 硬上限） | ✅ 已完成 | `TechniqueBudget`（`REALM_BUDGET` 在 :121，软上限 :115，`OVER_SOFT_MULTIPLIER` :126，`evaluate` :228/:240） |
| 词条词汇表（白名单 + 排他组 + 每词条上限） | ✅ 已完成 | `TechniqueEffect`（5 个词条）、`TechniqueEffectSpec`（`MAX_EFFECTS_PER_TECHNIQUE=3` :27，`EXCLUSIVE_GROUPS` :36） |
| spec 文本解析（看不懂就拒绝，不静默忽略） | ✅ 已完成 | `TechniqueEffectSpec.parse` :110，返回 `ParseResult(spec, problems)` |
| 服务端重算 + 归属/配额/保留字/重名 | ✅ 已完成 | `TechniqueCreationService.create` :94，`MAX_PER_PLAYER=3` :31，`RESERVED_WORDS` :48，`nameExists` :134 |
| 落库为"玩家对象" | ✅ 已完成 | `techniques.player_made / creator_user_id / effect_spec`（迁移步骤 025，`DatabaseMigration` :114、:549） |
| 运行时生效（战斗） | ✅ 已完成 | `TechniqueEffectResolver.forPlayer` :105；`CombatService` :510、:950 调用；30s 缓存 :32；聚合总上限 `CAP_*` :35-39 |
| **玩家入口（指令 / REST / WS）** | ❌ **不存在** | 全仓 `TechniqueCreationService` 只在自身与测试中被引用 |
| 治理（举报 / 人工下架 / 状态机） | ❌ 不存在 | 类注释自认："真正的 UGC 治理需要举报 + 人工下架"（`TechniqueCreationService` :45） |

**量级标定**：做一个 L2 对象（含纯逻辑、DAO、服务、测试）约 **1300 行**——
这是估算后续每个 L3 对象成本的最好参照。

### 1.3 复用 L2 模板前必须先修的三个问题

L2 目前**没有玩家入口**（下面 1.2 已列），所以这些问题暂时不可达；但 Phase 0
一旦把入口接上，它们会立刻变成线上问题。**建议接入口之前先修**：

| # | 问题 | 证据 | 修法 |
|---|---|---|---|
| 1 | **装备后删除功法，属性永久保留且可无限叠加**（严重） | `TechniqueService.equipTechnique` 把加成写进 `players` 行（`applyTechniqueBonuses`），而 `TechniqueCreationService.delete` 只删 `techniques` 行；`players_techniques` 外键级联删除学习记录，属性没人回退。实测：攻 10 → 装备 60 → 删除仍 60 → 再建再装备 110 | 删除前强制卸下并回退；已有他人学习时禁止硬删（改为归档/退休标记） |
| 2 | **同一效果两个价格**：词条「战意」100/1% 上限 20%，而属性 `combat_damage` 200/1% 上限 15%（软上限后 5000 点换 15%）；「护体」100/1% 上限 20% vs `damage_reduction` 200/1% 上限 15%。词条严格占优 | `TechniqueEffect` 的 costPerUnit / maxUnits vs `TechniqueBudget.Stat` 的 baseCost / hardCap | 二选一：玩家预算里禁用两个"战斗伤害/减伤"属性（保留列给官方功法），或把词条价格×2 |
| 3 | **删除会静默抹掉其他玩家学过的功法**（外交/经济问题）：`players_techniques.technique_id` 是 `ON DELETE CASCADE`，创作者删除后，所有学过的人手里直接消失、学费不退 | `DatabaseSchema.createPlayersTechniquesTable` 的外键 | 有任何人学过就不允许硬删；或软删除（列表/学习页隐藏，已学者保留） |

另外两个已知但优先级较低的问题：
- 创建是免费的（只算学习/升级费用），且创建/删除都没有冷却 → 可以反复改方案、
  抢注名字；接入口时建议加一次性"悟道"消耗与名字保留期。
- `creator_user_id` 列名说的是 user，实际存的是 `players.id`（`create()` 传
  `player.getId()`，`countByCreator`/`deleteOwned` 也按玩家 id 比较）——
  以后写管理端/统计时别去 JOIN `users`。

### 1.3 为什么不能"执行玩家代码"

- 现成教训：`plugins/` 目录的写权限 ≈ RCE（见 `docs/项目全景分析报告.md`）。
  插件至少是"服主信任的人"写的；玩家内容是全服玩家写的，风险高一个数量级。
- 项目里已有正确的"声明式"先例：`effect_spec` 是**数据字符串**、
  `map_connections` 是**数据行**、`recipes` 是**数据行**。
  L3 要做的就是继续用这种形态，绝不引入 `ScriptEngine` / 反射 / 类加载 /
  表达式求值。

## 2. L3 的通用模型（本项目版）

一条管线，所有对象类型共用：

```
玩家提交 spec(JSON)
      │
      ▼
① 严格解析：白名单 key + 数值范围 + 权重 + 长度上限；未知键一律拒绝
      │
      ▼
② 预算裁决：总量 / 边际递减 / 硬上限（沿用 TechniqueBudget 三重约束）
      │
      ▼
③ 治理前置：重名、保留字、控制字符、配额、创建冷却、费用（不可退 sink）
      │
      ▼
④ 落库：player_content(status=ACTIVE) + 领域表投影；player_made=1、creator_user_id
      │
      ▼
⑤ 动态注册表/缓存：DB 加载 → 内存索引；写后失效 + 换库回调失效
      │
      ▼
⑥ 运行时：走既有 resolver / registry / service（官方内容不动）
      │
      ▼
⑦ 治理后置：举报 → 自动隐藏阈值 → 管理员下架/恢复 → 审计
```

与 L2 的对应关系：

| 管线环节 | L2 已有可复用件 | L3 需要新增 |
|---|---|---|
| ① 解析 | `ParseResult(spec, problems)` 模式 | 通用 `PlayerContentSpec`（JSON + `spec_version`） |
| ② 预算 | `TechniqueBudget` 三重约束 | 每类对象一个 Budget 类（共享工具方法） |
| ③ 治理前置 | `RESERVED_WORDS`、名字唯一、配额 | 通用命名/配额/冷却/费用 |
| ④ 落库 | `player_made` + `creator_user_id` 惯例 | 通用 `player_content` 表 + 领域投影 |
| ⑤ 注册表 | ❌（L2 直接把行存进 `techniques`，按玩家查） | **动态内容注册表/缓存**（本项目空白） |
| ⑥ 运行时 | `TechniqueEffectResolver`（含聚合上限） | 各对象自己的 resolver |
| ⑦ 治理后置 | ❌ | `content_reports` + 状态机 + 管理端 |

## 3. 候选 L3 对象（按落地成本排序）

| # | 对象 | 复用度 | 新增复杂度 | 经济风险 | 建议 |
|---|---|---|---|---|---|
| 1 | 自创丹方 | 高（`recipes` 已是数据行） | 低 | **高**（产出/成本比） | 等经济模型 |
| 2 | 自建传送阵（§4.2 已立项） | 高（`map_connections` 是数据行） | 低 | 低-中 | **第一优先** |
| 3 | 自创秘境（洞天福地） | 中（事件生成是硬编码） | 中 | 中 | 第二优先 |
| 4 | 自创阵法 | 中（阵法模板硬编码） | 中 | 中 | 等 §4.1 |
| 5 | 自创奇遇/事件 | 低（事件是代码驱动的类） | **高** | 高 | 最后 |
| 6 | 自创功法上架交易（UGC 经济闭环） | 高（坊市已存在） | 低-中 | 中 | 可与 2/3 并行 |

### 3.1 自创丹方（成本最低，风险最高）

- **玩家决定**：从既有材料白名单选 1~3 种、选效果词条（沿用 L2 词条库：
  攻击/防御/速度/灵力、经验倍率、伤害反弹……，都有现成 `BuffService` 通路）、
  决定成品数量。
- **服务端重算**：材料数量与"药效预算"的换算、成功率的定价、产出上限；
  成品一律引用**既有物品 key**（不新增物品），或新增"玩家丹方产物"模板。
- **复用**：`recipes` 表（`DatabaseSchema` :61）本身已是数据行，`CraftingService.craft`
  :51 直接读库；`BuffService` 处理效果。
- **新增**：`recipes` 补 `player_made/creator_user_id/spec_json` 列 + 预算类 + 校验。
- **风险**：这是"把原材料变成更强成品"的**印钞路径**。必须先按
  `docs/analysis/xiuxian2pmv-经济系统分析报告.md` 的 EV 方法评估：
  材料成本 ≥ 成品期望价值 × 系数；否则就是第二个"金银阁"。
- **结论**：技术上最简单，**经济上最危险**，不建议作为第一个。

### 3.2 自建传送阵（§4.2，推荐第一优先）

- **玩家决定**：在**两个已探索地点**之间修一条边；路程秒数由距离/危险度决定
  （或玩家只能选"标准/快捷"两档，价格不同）；可设过路费（若公开）。
- **服务端重算**：费用（烧掉、不退款）、两端是否已探索、是否已存在边、
  边数配额、是否跨危险区（限制安全区↔安全区、需境界门槛）。
- **复用**：`map_connections`（`DatabaseSchema` :823）是纯数据边；
  `MapService.reload()` :218 已有热重载；`MapService.repairReverseConnections` :393
  会自动补反向边（**若要做单向收费边，必须让它跳过玩家边**）。
- **硬约束（代码里已存在，必须处理）**：
  - `map_connections` **没有唯一键**（`MapDAO` :470 注释），只能"先查后插"，
    并发下可能插重复 → 要么加唯一约束（迁移），要么在服务层加锁/事务去重；
  - `repairReverseConnections` 会把所有边补成双向；
  - 世界重建/出厂数据写入（`insertAllDefaultLocations` :388）不能碰玩家边
    （用 `player_made=1` 过滤）；
  - 与 `seedHash` 解耦（§4.2 已定）：玩家边不得影响野外生成确定性。
- **经济闭环**：修边是一次性灵石消耗（sink）；过路费给修建者（UGC 第一个
  "玩家间转移"的收入来源，且天然有上限：一条边一天收多少）。
- **新增量级**：表加 4~6 列 + `TeleportArraySpec` 解析/预算 + 服务 + 指令/REST +
  管理端列表 + 测试，约 **500~800 行**（不含共享基座）。
- **为什么推荐先做**：数据模型最小、没有运行时行为风险（只是多一条边）、
  与 §4.1"世界设施"方向一致、天然带经济闭环，能先把 L3 基座和治理走通。

### 3.3 自创秘境（洞天福地，第二优先）

- **玩家决定**：秘境名/描述、进入境界、冷却时长、**事件权重表**
  （宝箱/妖兽/首领/灵草/遗迹/陷阱/无事，从白名单选 2~5 种并分配权重）、
  奖励倾向档位（低/中/高，受预算限制）。
- **服务端重算**：权重总和、事件种类数、奖励档位与预算、与境界的匹配；
  实际掉落**不用玩家给的数字**，由服务端按档位从既有掉落表抽。
- **复用**：`SecretRealmService` 的 8 个事件处理器（`generateRealmEvent` :163）
  全都是现成逻辑；`SecretRealmRegistry`（:23）是现成内存表；指令
  `/进入秘境`（`SecretEnterCommand`）与每日计数（`DailyService.onSecretRealm` :187）
  都现成。
- **需要改造的地方（关键）**：现在**事件概率是硬编码的 if/else 链**
  （`generateRealmEvent` :163-215，按 `area.getRequiredRealm() >= 6` 分支）。
  L3 版本要先抽出 `RealmEventTable`（事件类型 → 权重），官方秘境用默认表，
  玩家秘境读 spec 权重。这是对既有玩法**行为零改变**的纯重构（默认表复刻
  现有百分比），但必须先做、并有回归测试。
- **约束**：`players.last_secret_realm_time` 是**每玩家一个全局冷却**
  （`SecretRealmService.enterSecretRealm` :56 起的事务），玩家秘境若要有
  独立冷却/独立次数，需要新表 `player_secret_realm_visits(player_id, content_id, last_at)`。
- **社交**：`enterRaid`（:507）已有组队挑战通路，可做"邀请好友 + 入场费"。
- **新增量级**：抽事件表（~200 行）+ spec/budget（~300）+ 动态注册（~150）+
  服务改造（~250）+ 指令/REST（~150）+ 测试，约 **1000~1400 行**。

### 3.4 自创阵法

- **玩家决定**：阵法名 + 从白名单效果（灵气加速/修炼加成/防御/抗心魔）分配预算。
- **复用**：`formations` 表（`DatabaseSchema` :889）**已经按实例存了数值列**
  （`spirit_energy_boost` 等），本质上已经是"实例化后的数值"，只缺
  `player_made/creator_user_id/spec_json` 与动态模板。
- **阻塞**：§4.1（阵法该不该是"世界设施"）未拍板，且 `formations` 没有
  `location_id`（HANDOFF §五）。建议等 §4.1。
- **新增量级**：约 **600~900 行**。

### 3.5 自创奇遇/事件（最后做）

- **为什么难**：`ExplorationEvent` 是**抽象类 + `execute()` 代码**
  （`ExplorationEvent` :53），由 `ExplorationEventScanner` 启动期注册；
  这不是数据，不能直接给玩家。要做 L3 必须先把事件改成"声明式动作序列"：
  白名单动作（给物品/加经验/战斗/传送/给 buff/文案）× 参数 × 条件。
- **风险**：动作序列 = 变相脚本，虽然不执行代码，但组合爆炸后的数值影响
  极难配平；治理面也最大（任何恶意文案都会展示给陌生人）。
- **结论**：等前几个对象把"预算 + 治理"跑顺再考虑；或永远只做"权重选择"
  而不做"动作自定义"（那就退化成 3.3 的自创秘境）。

### 3.6 UGC 经济闭环（与对象类型正交）

自创功法（L2）已经在库里，但没有交易通路。把它接进坊市（寄售/传承/拍卖），
就能让"创造"产生经济价值，反哺玩家投入。改动集中在 `TradeService` +
`techniques` 的归属转移（`creator_user_id` 不变、`owner` 变），**约 400~600 行**，
且不引入新内容类型——性价比很高，但它放大了治理需求（盗号销赃、洗钱），
需要和举报/下架一起做。

## 4. 共享基座设计（真正要写的东西）

### 4.1 数据模型：单表 + 领域投影

```sql
CREATE TABLE player_content (
  id            BIGINT PRIMARY KEY,          -- 或自增，按项目方言
  type          VARCHAR(32)  NOT NULL,       -- teleport_array / secret_realm / pill_recipe ...
  owner_user_id BIGINT       NOT NULL,       -- 归属（⚠️ 存 players.id：现有 techniques.creator_user_id
                                             --    列名叫 user_id，实际写的是 player.getId()）
  name          VARCHAR(32)  NOT NULL,
  description   VARCHAR(128) DEFAULT '',
  spec_json     TEXT         NOT NULL,       -- 声明式规格（见 4.2）
  spec_version  INT          DEFAULT 1,
  status        VARCHAR(16)  DEFAULT 'ACTIVE', -- ACTIVE / HIDDEN / REMOVED
  created_at    BIGINT, updated_at BIGINT,
  hidden_reason VARCHAR(128)
);
CREATE TABLE content_reports (
  id BIGINT PRIMARY KEY, content_id BIGINT NOT NULL,
  reporter_user_id BIGINT NOT NULL, reason VARCHAR(128),
  created_at BIGINT, handled BOOLEAN DEFAULT 0
);
```

- 领域表只存"投影/索引列"（如传送阵的 `from/to`），权威数据在 `spec_json`；
  或者反过来（领域强结构、公共表只做治理索引）——**建议前者**：
  一个举报/下架/配额入口，治理代码只写一遍。
- 迁移：`DatabaseMigration` 加 Step（:114 的 steps 列表），SQLite/MySQL 双方言；
  同时更新 `DatabaseSchema` 的建表（新装库）与迁移（老库），两处都要。

### 4.2 Spec 格式与校验

- JSON（项目已用 Gson），`spec_version` 便于以后兼容；
- **严格白名单**：未知 key / 未知枚举 / 越界数值 → 直接拒绝并返回可读 problems
  （沿用 `TechniqueEffectSpec.ParseResult` :110 的形态）；
- 大小上限（如 ≤ 2KB）、集合长度上限、字符串长度上限、控制字符过滤；
- 所有物品/地点/怪物引用必须是**注册表里真实存在的 id**（防伪造）；
- 客户端提交的**任何结果值都不采信**（数值、成功率的最终裁决在服务端）。

示例（传送阵）：

```json
{ "version": 1, "from": 3, "to": 17, "tier": "FAST", "toll": 50 }
```

### 4.3 预算模型

直接复用 `TechniqueBudget` 的三重约束：**总量上限、超过软上限单价翻倍、
单项硬上限**。每类对象一个 Budget 类（如 `TeleportArrayBudget`、
`SecretRealmBudget`），共享同一个 `BudgetMath` 工具，避免每类各写一套。

### 4.4 动态注册表 / 缓存失效（项目空白）

现有 `SecretRealmRegistry` / `ExplorationEventRegistry` 都是**启动期内存注册表**
（`SecretRealmRegistry.register` :23），玩家内容必须支持运行期增删：

- `PlayerContentRegistry`：启动时从 DB 全量加载 → 内存只读快照；
  写操作后失效重建（单机场景量很小，可以全量重载）；
- 换库回调：`DatabaseManager.addReinitListener`（容器已用同一机制）注册重载；
- 与官方注册表**分表共存**：查找顺序 = 玩家内容（DB）→ 官方（内存）；
- 注意容器 `close()` 要摘回调（项目已有 `removeReinitListener` 先例）。

### 4.5 治理最小版

| 能力 | 最小实现 | 位置 |
|---|---|---|
| 状态机 | `ACTIVE/HIDDEN/REMOVED`，HIDDEN 不再被他人看到/使用 | service |
| 举报 | 玩家 `/举报 <id> <原因>`，写 `content_reports`，同一内容 ≥N 次自动 HIDDEN | 新指令 + 表 |
| 人工下架/恢复 | `AdminPlayerContentResource`（沿用现有 admin REST 模式） | rest |
| 审计 | 创建/举报/下架记 `PlayerActionLogger` 或专用表 | util |
| 命名 | 保留字（抄 `RESERVED_WORDS` :48 一份共享）+ 全表唯一 + 长度 + 控制字符 | spec |
| 配额 | 每玩家每类型上限（传送阵 3、秘境 1）、创建冷却 | service |

**私有模式可以省掉举报/下架**：内容只对 owner 可见 → 没有传播，就没有脏话墙。
建议第一阶段（Phase 1）就做私有，公开/收费放到 Phase 2 再打开。

### 4.6 经济与配额

- **创造费**：不可退的灵石 sink（参考 §4.2"费用烧掉、不退款"）；
- **维护费**（世界设施类）：按天扣，欠费自动失效——让"占着位置不玩"有成本；
- **收益**：过路费/入场费 → owner（每日上限，防挂机刷）；
- **反滥用**：创建/删除冷却、每玩家配额、名字抢注保护（唯一 + 保留字）、
  举报自动隐藏；
- **平衡校验**：新增任何"玩家可产出的价值"，先按经济分析报告的 EV 方法算一遍。

### 4.7 安全红线（建议写成守护测试）

- 禁止 `ScriptEngine`、`Class.forName`、`Method.invoke`、表达式求值、动态编译；
- 禁止玩家 spec 里出现任何"代码/反射"语义；只认枚举 + 数字 + 白名单 id；
- spec 解析必须是纯函数（可单测、无 IO）；
- 服务端重算：客户端给的所有数值只用于"预览"，落库值全部服务端算；
- 聚合上限：每个生效路径都要有总量上限（`TechniqueEffectResolver` 的
  `CAP_*` :35-39 是范本）。

### 4.8 可观测与 i18n

- 管理端能看：玩家内容列表、举报列表、按类型统计、下架记录；
- 玩家文本（名字/描述）是**用户数据**，不进语言包（`docs/i18n-design.md` :144
  已有同样判断）；UI 文案走 i18n key；
- 日志：创建/下架/删除打一条结构化日志（`GameLogger`）。

### 4.9 测试策略

- 纯逻辑：spec 解析/预算/命名（对标 `TechniqueBudgetTest` / `TechniqueEffectTest`）；
- DAO：新表按 `XxxDaoExtractionTest` 模式抽 DAO + 黄金 SQL 清单；
- 服务边界：对标 `TechniqueCreationServiceTest`（重名/冒充/超预算/数量上限/
  删别人的，全部覆盖）；
- 运行时：官方内容行为零回归（尤其是秘境事件表重构、传送阵对
  `MapService` 缓存/邻接的影响）；
- 守护：`ServiceInjectionMigrationTest` 同类的方式，钉住"没有代码执行";

## 6. 需要拍板的问题（决定之后才好动代码）

1. **先做哪个对象**：我建议 Phase 0（补 L2 入口）→ Phase 1 自建传送阵。
2. **公开还是私有**：私有 = 零治理成本、先验证玩法；公开 = 必须有举报/下架。
   建议 Phase 1 私有，Phase 2 再加公开与收费。
3. **玩家内容能否产生收益**（过路费/入场费/交易）？这决定经济闭环要不要一起做。
4. **治理强度**：举报+管理员下架是最小集；要不要"实名/等级门槛才能创建"？
5. **模块门控**：L3 是否作为独立内置模块（`BuiltInPluginRegistry` 可停用），
   建议是——出问题时能一键关掉，不用回滚代码。

---

## 7. 明确不做（L4）

- 不在执行进程里跑玩家代码（脚本/表达式/插件式 DSL 解释器都不做）；
- 不开放任意数值/任意概率；
- 不让玩家内容引用"代码注册表"之外的东西（类名、SQL、文件路径、i18n key 覆盖）。
